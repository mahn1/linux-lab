Маршрутизация в Linux: ПК1 → R1 → R2 → ПК2

Лабораторная работа «Реализация сетей в Linux». Пинг с одного компьютера на другой через два маршрутизатора и коммутатор, настройка через Netplan.

1. Схема стенда

сеть A /28   сеть B /30   сеть C /29  ·  «Net N» — подпись кабеля/гнезда на стенде, в конфигах не используется.

Подсети не пересекаются: 0–15, 16–23, 24–27. Сеть /30 между маршрутизаторами — ровно на два адреса, по одному на каждый конец канала.

3. Подготовка (на всех четырёх машинах)

  1. Подключить кабели по схеме.
  2. Проверить имена интерфейсов — должны совпадать с таблицей: 
    ip a
  3. Посмотреть, какие конфиги Netplan уже есть: 
    ls /etc/netplan/
    Если там лежит другой файл с теми же интерфейсами (например 50-cloud-init.yaml), убрать его, чтобы не было конфликта: 
    sudo mv /etc/netplan/50-cloud-init.yaml /etc/netplan/50-cloud-init.yaml.bak
Конфиг можно набрать в sudo nano /etc/netplan/01-lab.yaml или вставить одной командой (блоки ниже — команда tee сразу создаёт файл). В YAML отступы — только пробелы, без табуляции.

4. Конфигурация Netplan

ПК1 enp4s0 · 10.0.0.1/28

sudo tee /etc/netplan/01-lab.yaml > /dev/null <<'EOF'
network:
  version: 2
  renderer: networkd
  ethernets:
    enp4s0:
      addresses: [10.0.0.1/28]
      routes:
        - to: default
          via: 10.0.0.3
EOF

ПК2 enp1s0 · 10.0.0.19/29

sudo tee /etc/netplan/01-lab.yaml > /dev/null <<'EOF'
network:
  version: 2
  renderer: networkd
  ethernets:
    enp1s0:
      addresses: [10.0.0.19/29]
      routes:
        - to: default
          via: 10.0.0.17
EOF

R1 enp1s0 · 10.0.0.3/28  |  enp4s0 · 10.0.0.25/30

sudo tee /etc/netplan/01-lab.yaml > /dev/null <<'EOF'
network:
  version: 2
  renderer: networkd
  ethernets:
    enp1s0:
      addresses: [10.0.0.3/28]
    enp4s0:
      addresses: [10.0.0.25/30]
      routes:
        - to: 10.0.0.16/29
          via: 10.0.0.26
EOF

R2 enp1s0 · 10.0.0.26/30  |  enp3s0 · 10.0.0.17/29

sudo tee /etc/netplan/01-lab.yaml > /dev/null <<'EOF'
network:
  version: 2
  renderer: networkd
  ethernets:
    enp1s0:
      addresses: [10.0.0.26/30]
      routes:
        - to: 10.0.0.0/28
          via: 10.0.0.25
    enp3s0:
      addresses: [10.0.0.17/29]
EOF
Старый Netplan (Ubuntu 20.04 и раньше) может не принять routes: - to: default. Тогда на ПК1 вместо блока routes пишется gateway4: 10.0.0.3, на ПК2 — gateway4: 10.0.0.17.

5. Применение (на всех четырёх)

sudo chmod 600 /etc/netplan/01-lab.yaml
sudo netplan apply

Безопасный вариант — sudo netplan try: если связь пропадёт, настройки откатятся через 120 секунд.

6. Пересылка пакетов (только R1 и R2)

По умолчанию Linux не передаёт пакеты между интерфейсами — без этого шага пинг дальше первого маршрутизатора не пройдёт.

sudo sysctl -w net.ipv4.ip_forward=1

Команда сразу выводит net.ipv4.ip_forward = 1 — это и есть проверка. Настройка действует до перезагрузки; после перезагрузки команду нужно выполнить снова.

7. Проверка

Адреса и маршруты (на каждой машине)

ip -br a
ip r

На маршрутизаторе в ip r должно быть три строки: две сети, подключённые напрямую (proto kernel), и один статический маршрут в «чужую» сеть (via, proto static).

R1 — ip r

10.0.0.0/28 dev enp1s0 proto kernel scope link src 10.0.0.3
10.0.0.16/29 via 10.0.0.26 dev enp4s0 proto static
10.0.0.24/30 dev enp4s0 proto kernel scope link src 10.0.0.25

R2 — ip r

10.0.0.0/28 via 10.0.0.25 dev enp1s0 proto static
10.0.0.16/29 dev enp3s0 proto kernel scope link src 10.0.0.17
10.0.0.24/30 dev enp1s0 proto kernel scope link src 10.0.0.26

Нет строки с via — Netplan не применился или ошибка в блоке routes. На ПК в ip r две строки: default via … и своя сеть.

Кратко по всем машинам:

МашинаЧто должно быть в ip r
ПК1default via 10.0.0.3 dev enp4s0, 10.0.0.0/28 dev enp4s0
R110.0.0.0/28 dev enp1s0, 10.0.0.24/30 dev enp4s0, 10.0.0.16/29 via 10.0.0.26 dev enp4s0
R210.0.0.24/30 dev enp1s0, 10.0.0.16/29 dev enp3s0, 10.0.0.0/28 via 10.0.0.25 dev enp1s0
ПК2default via 10.0.0.17 dev enp1s0, 10.0.0.16/29 dev enp1s0

Пинг по цепочке с ПК1

Идти по шагам: где пинг перестал проходить — там и ошибка.

ping -c 3 10.0.0.3     # R1, вход (своя сеть A)
ping -c 3 10.0.0.25    # R1, выход
ping -c 3 10.0.0.26    # R2, вход (нужен маршрут обратно на R2)
ping -c 3 10.0.0.17    # R2, выход
ping -c 3 10.0.0.19    # ПК2 — цель лабораторной

Маршрут пакета

tracepath 10.0.0.19

Ожидаемые прыжки: 10.0.0.3 → 10.0.0.26 → 10.0.0.19. Обратная проверка — с ПК2: ping -c 3 10.0.0.1.

8. Если не работает

СимптомПричина и что делать
netplan apply ругается на YAMLТабуляция или сбитые отступы. Проверить: sudo netplan generate.
Не пингуется даже соседний интерфейсКабель не в том гнезде / интерфейс не поднят: ip -br a (должно быть UP), проверить имя интерфейса и подключение по схеме.
Пинг до 10.0.0.3 и 10.0.0.25 есть, дальше — нетНа R1 не выполнена sudo sysctl -w net.ipv4.ip_forward=1 (или машину перезагружали) или на R2 нет маршрута 10.0.0.0/28 via 10.0.0.25 (ответ не может вернуться).
До R2 доходит, до ПК2 — нетНа R2 нет ip_forward, у ПК2 нет шлюза 10.0.0.17 или неверная маска (/29).
Всё настроено, но тишинаФайрвол: sudo ufw status; на время лабораторной sudo ufw disable. Ещё один конфиг Netplan с теми же интерфейсами — см. п. 3.

9. Кратко для защиты

  • Зачем маршрутизатор: ПК1 и ПК2 в разных подсетях, напрямую (через ARP) друг друга не видят — пакет передаётся шлюзу.
  • Шлюз по умолчанию у конечных ПК — ближайший интерфейс маршрутизатора в их сети.
  • Статические маршруты на R1 и R2 нужны для «чужих» сетей: R1 не знает про сеть C, R2 — про сеть A. Маршрут нужен в обе стороны, иначе ответ на ping не вернётся.
  • ip_forward разрешает ядру пересылать пакеты между интерфейсами.
  • /30 между маршрутизаторами — минимальная сеть для двух адресов.
  • Коммутатор работает на канальном уровне (MAC), IP-адресов не требует; разделение сетей задаётся IP-подсетями.
